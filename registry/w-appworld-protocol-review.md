## 1. Exact task-facing lifecycle

1. **Receive the public contract.** `_setup` supplies the `aw` file and `_runtime_prompt`; the task's goal is its instruction (`data/datasets/appworld.py:202–203`, `:242–249`). `runtime_task` appends only the explicit public prompt to `goal`: `+ "\n\nRuntime tool instructions:\n" + prompt` (`eval/run/task_contract.py:12–18`). The prompt says “Use your harness's shell/command tool” and “Python snippets belong in --code” (`data/datasets/appworld.py:210–212`). This is generic protocol text, not selected-task solution logic; the task-independent comparison is explicit in `tests/quality/test_appworld_actor_protocol.py:62–77`.
2. **Initialize once.** Run `./aw init --task <task_id>`; the decisive warning is “Reinitializing resets the world, so keep using action after initialization” (`data/datasets/appworld.py:214–216`). The CLI posts to `/initialize`, records the task in `.appworld_task`, and prints returned metadata (`data/datasets/appworld/cli/aw:10–11`, `:45–49`). The wrapper checks the platform-bound task, creates `AppWorld(... load_ground_truth=False, ground_truth_mode="minimal", raise_on_failure=False)`, and returns task ID/instruction, supervisor first/last name/email/phone, and datetime (`data/datasets/appworld/service.py:17–19`, `:37–56`). Wrong-task requests receive 403; action before initialization receives 409 (`:25–29`). The health endpoint merely returns status/task ID, so health alone does not establish an initialized world (`:32–34`).
3. **Submit an action to the persistent service.** Run `./aw action --task <task_id> --code '<python>'`. The prompt says “Variables and API state persist between action calls” and “one action is not one API call” (`data/datasets/appworld.py:218–223`). The CLI sends the supplied snippet as `/execute` JSON and prints the returned `output`; the wrapper delegates to `world.execute(code)` (`data/datasets/appworld/cli/aw:14–22`, `:50–55`; `data/datasets/appworld/service.py:59–62`). Assignments/loops/conditionals and multiple calls belong in that remote snippet; local Python does not provide this namespace (`data/datasets/appworld.py:219–223`). **Marker caveat:** absent/mismatched `.appworld_task` causes an implicit initialize even for `action`; changing the CLI's working directory or deleting its marker can therefore trigger a reset (`data/datasets/appworld/cli/aw:11`, `:50–52`; reset warning at `data/datasets/appworld.py:215–216`). Occurrence in the reviewed losses is not established.
4. **Discover the service surface.** The executable starting point is `print(apis.api_docs.show_app_descriptions())`, followed by `show_api_descriptions(app_name=...)` and `show_api_doc(app_name=..., api_name=...)`; calls use `apis.<app>.<api>(...)`. The prompt instructs discovery of supervisor APIs for credentials and use of returned/documented values (`data/datasets/appworld.py:209`, `:225–232`). The wrapper additionally exposes initialized `/api_docs`, returning `world.task.api_docs.copy()` (`data/datasets/appworld/service.py:65–69`). Its enumerated handlers are health, initialize, execute and api_docs (`:32`, `:37`, `:59`, `:65`); the wrapper's stated purpose is to avoid exposing upstream evaluation/state/log-management endpoints (`:3–6`). No deployed boundary proof is inferred from this source review.
5. **Change and observe state through APIs.** “Perform the requested changes through these API actions, inspect their results”; “Print the responses you need to inspect” (`data/datasets/appworld.py:221–222`, `:234–237`). Use discovered read APIs to read back the changed state inside subsequent remote actions; the observable surface is the returned/printed API response, not an actor-written database or receipt (`data/datasets/appworld/cli/aw:53–55`; `data/datasets/appworld/service.py:62`). The service recording path is tied to `/appworld/experiments` by `ln -s /recordings/appworld/experiments /appworld/experiments` (`data/datasets/appworld/server.sh:26–29`). Platform mounts give the harness no recording and the verifier a read-only recording (`eval/service/services.py:489–496`); the prompt explicitly says it “is not an actor file to create or edit” (`data/datasets/appworld.py:236–237`).
6. **Finish at both boundaries when the discovered world API requires completion.** The existing prompt's instruction is only “then give your final answer through your harness” (`data/datasets/appworld.py:234–235`). In the generic loop, a parsed answer with no command records `submitted=True`, extracts the answer and breaks; afterward `(workdir / "answer.txt").write_text(answer)` (`base_harness/loop/agent.py:668–682`, `:747`). This ends actor execution; it does not call an AppWorld API. Any in-world completion/answer must already have been submitted through the discovered API surface if it is to be represented in the replay log. W1/W2 discovery advertises `complete_task`, yet their logs omit it (W1/trace:17; W2/trace:17; both log scopes enumerated in section 3). This statement explains the generic boundary; it supplies no selected-task answer, argument values or corrected action.
7. **Score the recorded world, separately from the final text.** The adapter declares a command verifier with `--log /recordings/appworld/experiments/outputs/harness/tasks/<task_id>/logs/api_calls.jsonl`, reward/evidence files, a separate verifier image and a 900-second timeout (`data/datasets/appworld.py:267–289`). The platform launches a fresh verifier with recording mounts and the task service network (`eval/verification/verifier.py:641–668`). The checker reads JSONL, creates a fresh AppWorld, replays each request, then executes `tracker = world.evaluate()` (`data/datasets/appworld/verify/check.py:31–56`). The identity is `"metric": "appworld.task_goal_completion", "metric_name": "TGC"` (`:29–30`); measured evidence contains Boolean `tracker.success`, test count, passes and failures, with reward `"1.0\n" if tracker.success else "0.0\n"` (`:61–75`). Its parser accepts task/split/log/reward/evidence arguments, **no final-answer argument** (`:23–27`). Missing/unreadable log, unknown HTTP method or environment exception writes `measured=False` and exits 3, rather than declaring a task loss (`:12–18`, `:32–37`, `:50–51`, `:59–60`). Staged publication is a further layer: the actual W1/W2 receipts keep null scores for unobserved enforcement (both receipt:47–83).

**Step accounting:** loop defaults are `MAX_STEPS=32`, `MAX_OUTPUT_TOKENS=2048`; `for step in range(MAX_STEPS)` obtains a model reply and may execute a shell command or accept an answer (`base_harness/loop/agent.py:63–64`, `:604–613`, `:668–693`). ## 3. Generic defect/gap analysis and discriminating observables

### FOUND: completion guidance does not distinguish the two submissions

The exact prompt passage is:

> Perform the requested changes through these API actions, inspect their results,
> then give your final answer through your harness. A local script, plain text
> answer or print-only snippet does not change the world.

(`data/datasets/appworld.py:234–236`.)

The second warning concerns changes, but the passage does not explain that a final harness answer also remains outside the replayed world's answer/completion. The generic loop's accepted answer path only writes a local file; the checker only consumes recorded requests (`base_harness/loop/agent.py:679–682`, `:747`; `data/datasets/appworld/verify/check.py:23–27`, `:47–56`). Accordingly, a task whose state changes are correct can still return measured zero if its in-world completion is omitted. W1 is the observed instance: seven requirements pass and the sole failure is answer comparison, while a local submission is accepted (W1/evidence:1; W1/trace:33). This describes a task-independent mechanism, not a selected-task correction.

**ABSENT, bounded:** supervisor completion requests in both retained logs. Enumerate all nonempty JSONL rows, W1/log rows 1–14 and W2/log rows 1–14; test each parsed `url` for `complete_task` or `/supervisor/complete` (credential reads under `/supervisor/account_passwords` are not completion). The exact command and the complete method/URL list with `supervisor_completion_rows=[]` appear in the validation transcript. **FOUND:** discovery text at both trace row 17 contains `complete_task`; that rules out “the API was not discoverable” for these recorded interactions. **UNKNOWN:** whether an unchanged model, supplied an unambiguous generic completion contract, would produce a successful measured actor task. No correction, replay or live comparison was executed.

**Discriminating observable (proposed only):** in a fabricated world with a state requirement and a separate completion requirement, record (a) printed state readback, (b) completion API request/response, (c) local harness submission, (d) replayed completion state and evaluator result. Correct live state with no completion request isolates the actor/guidance boundary; an emitted successful completion that disappears from the recording or replay isolates recording/verifier wiring; incorrect live state despite preserved completion remains a task-state failure. This control uses no selected-task answer or dataset task, and cannot itself satisfy successful-task-evidence.

### FOUND in source, occurrence UNKNOWN: marker-driven reset hazard

The CLI's `MARKER = pathlib.Path(".appworld_task")` is relative to the process working directory; `action` implicitly initializes when that file is absent/mismatched (`data/datasets/appworld/cli/aw:11`, `:50–52`). Initialization resets the world by the public contract (`data/datasets/appworld.py:214–216`). A marker loss or working-directory switch can therefore break persistence for any task. This is a conditional protocol hazard, **not an observed cause of these zeros**. The discriminating observable is an unexpected extra `/initialize` between actions plus loss of an earlier synthetic variable/state value; a retained value with only one initialize argues against it. A fabricated marker/cwd control would suffice; no real task rerun or budget change is proposed.

### No additional demonstrated generic defect at this scope

The reviewed source forwards snippets unchanged, preserves returned output, separates actions from API calls, withholds actor recording mounts, and wires a fresh checker to the service recording (`data/datasets/appworld/cli/aw:53–55`; `data/datasets/appworld/service.py:62`; `data/datasets/appworld.py:220–222`; `eval/service/services.py:489–496`; `eval/verification/verifier.py:653–668`). Error text can occur with a successful HTTP/shell invocation because the service uses `raise_on_failure=False`; shell exit 0 therefore does not establish semantic API success (`data/datasets/appworld/service.py:48–50`; `data/datasets/appworld/cli/aw:53–56`). These are interpretation boundaries, not a demonstrated silent transport failure.

**UNKNOWN:** full live-state/replay equivalence, all upstream logging/exception semantics, and whether query stripping affects any real request. The checker strips `?` from each URL and replays `call.get('data') or {}`, then does not inspect the return value of each `world.execute` (`data/datasets/appworld/verify/check.py:48–55`). This source observation alone does not prove information loss or replay failure: this review has no independent upstream request-contract test for every form. The retained official losses must not be relabeled invalid on that speculation. W2's independent state error also prevents attributing its entire loss to the completion gap (W2/evidence:1).
