# Separating dataset and measurement provenance

Historical ChessBench, MATH, LoCoMo, SpreadsheetBench, Reasoning Gym and StrongREJECT scoring profiles hashed loader and scorer code together. This was conservative, but a loader move or edit could be reported as a scoring change. The move does not establish that either the dataset or the scoring algorithm changed. New ChessBench, MATH, MATH-500, LoCoMo, SpreadsheetBench, SpreadsheetBench 2, Reasoning Gym, StrongREJECT, AgentDojo, ALFWorld, Jericho and ScienceWorld runs use the separation described here; other adapters retain their existing profiles unless explicitly migrated.

## Evidence to retain

| Question | Evidence | Limit |
| --- | --- | --- |
| What data was requested? | Dataset name, declared upstream location, revision and declared artifact digest where available. | A declaration alone does not prove which bytes were read. |
| What was measured? | Selected task IDs and the existing private `verification_context` commitments over selected inputs and verifier declarations. | A commitment proves equality of captured inputs, not upstream authenticity or the entire dataset archive. |
| How was it loaded and executed? | Loader and provider implementation fingerprints plus `dataset_runtime_identity` for admitted provider and role artifacts. | Runtime identities do not seal the whole operating system or all external dependencies. |
| How was it scored? | Metric/protocol and scorer or judge implementation/configuration fingerprints. | A shared file that also loads data cannot safely be treated as scorer-only code. |
| Which platform performed the run? | Existing platform content identity and resume policy. | A platform change alone does not identify which measurement component changed. |

A scoring-identity mismatch means the recorded scoring profile differs; it does not by itself identify whether the metric, judge, endpoint or scorer code caused the mismatch. Comparability remains unknown until the underlying evidence is reviewed.

`harnessgrad.provenance.source_declarations` provides a shared, non-executing reader for top-level literal declarations. Dataset profiles still validate their own meanings and bind the resulting identities to their selected execution context.

Names of repository files should locate evidence, not by themselves define its meaning. A relocation with identical bytes can preserve a component fingerprint, but must not bypass the separate platform admission policy or imply that old measurements are automatically comparable. Multiple roles may conservatively refer to the same source bytes while loader and scorer remain in one file.

## Migration requirements

1. Add explicit, validated and versioned identities for the separate evidence; distinguish a declared source digest from an actually verified artifact digest. Do not fabricate data verification from a version string or from the selected-input commitment.
2. Capture the identities from the same selected loading session as the measurement, and carry them through run metadata, points, H0 preparation and subset projection, resume, cache and evidence export. Missing or malformed required evidence must fail closed where reuse or comparison depends on it.
3. Keep historical scoring envelopes readable and verify their original digest. An old combined identity cannot be decomposed retroactively merely by matching a filename; a comparison requiring the new components must report insufficient evidence unless a separately reviewed proof is available. Never rewrite historical receipts.
4. Exercise data-source, loader, scorer, runtime and platform changes independently with synthetic fixtures, including file relocation with unchanged bytes, content changes, absent evidence, digest tampering, H0 subset reuse and resumed runs. Confirm that private task inputs stay out of actor-facing and public evidence.
5. Roll out one adapter at a time after reviewing which files participate in each role. The other adapters' existing profiles and comparisons must continue to work until explicitly migrated.

The driver and H0 configuration collect opt-in ChessBench, MATH, LoCoMo, SpreadsheetBench, Reasoning Gym, StrongREJECT, AgentDojo, ALFWorld, Jericho and ScienceWorld profiles. Records, H0 reuse, resume, measurement cache and privacy-safe evidence export carry or compare their components. The scorer fingerprint also binds the separate scoring identity, so inconsistent captures are refused. ChessBench reads its literal revision and declared CSV digest without opening benchmark data; its loader and scorer identities conservatively overlap for shared code. MATH and MATH-500 read their upstream revision declarations from the native QA catalog and do not claim a declared digest for the upstream dataset. Their command-scorer identity covers the executed grading modules, including modules imported unconditionally, while the adapter and source-preparation code are recorded as loader components. LoCoMo records its declared source digest separately from its deterministic NLTK-based scorer and report aggregation; its scorer component also hashes the declared upstream Harbor scorer provenance, which is not a verification of downloaded upstream bytes. The upstream dependency declaration is not a claim about the installed version. Runtime artifacts and selected-input commitments remain separate. Existing combined scoring identities remain readable but cannot prove equivalence to the new components. This describes provenance and admission, not a change to the benchmark scoring algorithm.

SpreadsheetBench v1 records its pinned archive URL, revision and declared archive digest; v2 records its upstream dataset revision and archive name without an asserted digest. V2 also records the upstream evaluator declaration separately from its actual local evaluator source. These declarations do not establish the bytes of a workbook used in a run. The scorer fingerprints include the trusted verifier, input binding and native runtime helper, while selected verifier inputs and the actual Python and LibreOffice/UNO installations remain bound by verification context and runtime identities. The actual adapter still selects and binds those inputs; its bytes are captured as loader identity, not claimed as scoring algorithm bytes. Existing historical profiles stay valid as historical envelopes, but their combined identity cannot establish equality with the separated roles.

Reasoning Gym records the digest of its historical pool without claiming how that pool was acquired. Its scoring route imports the same adapter and QA scaffold used by the loader, so these shared source files are conservatively fingerprinted in both roles. The separately bound execution runtime identifies the installed package; the pool digest does not prove that a particular package or seed generated it.

StrongREJECT records a digest of its declared Harbor task inventory and upstream CSV declaration, not a verified artifact digest. Its adapter is shared by loading and verification, so it is fingerprinted in both roles. The scorer identity includes declared upstream evaluator/template metadata and local scoring and transport code; the separately recorded judge model, parameters and endpoint hash remain part of scoring identity. None of these declarations establishes actual judge behavior or downloaded bytes, and selected verifier inputs remain separately committed.

AgentDojo records its source archive declaration and prepared-manifest digest separately from loader and scorer code. These are pinned declarations, not proof that particular upstream or prepared bytes were used. Its adapter, bootstrap and bridge are shared by loading and verification and therefore appear in both implementation identities. The upstream inventory covers code and suite data together and is included conservatively in the scorer fingerprint. The selected cases and admitted execution runtime remain covered by their separate verification and runtime identities. Older AgentDojo records without these components are not automatically comparable to new captures; no historical record is rewritten.

ALFWorld records a digest of its four declared upstream archive descriptors as a data-source declaration, including the source archive that supplies domain and grammar material. This does not prove the downloaded bytes or selected games. Its adapter, replay helper and scorer-input binding participate in both loading and verification and are conservatively included in both code identities. The actual selected game inputs and native runtime remain separately bound. A file relocation with unchanged bytes and the same role preserves the component identity, while the platform identity still changes. Historical records missing these identities are not automatically comparable.

Jericho records the original ROM archive URL and its declared SHA-256 as the source identity; it does not infer an upstream commit or claim a selected ROM was verified. Its adapter, replay environment and scorer-input binding are shared and conservatively fingerprinted in both implementation roles. The selected ROM and admitted interpreter remain separately bound. Code relocation with identical bytes and role preserves the component identity; the platform identity remains separate. Older records missing these identities are not automatically comparable.

ScienceWorld records a normalized declaration of its public test and study task inventories, the declared gold-path archive and world-JAR digest. Descriptive comments and JSON formatting do not define the source identity. These are declarations, not proof that a particular downloaded archive or world was used. Its adapter, environment helper and world lookup participate in both loading and verification and are conservatively fingerprinted in both implementation roles; selected task inputs and actual Python/JVM runtime remain separately bound. Historical records without these identities are not automatically comparable.

AppWorld remains outside the separated profiles for now. Its adapter declares an encrypted bundle and pool digest, while the task evaluator and AppWorld package execute inside a separately selected verifier image; those bundle declarations alone do not identify the evaluator code actually executed. The existing verification-context commitment captures the selected verifier declaration, including its image reference and task split, but is an equality commitment rather than proof of the image's contents. A future profile must be tied to the actual selected and admitted verifier identity and handle H0 preflight and environment overrides before it can claim scoring provenance. Do not use the bundle digest as a substitute for that identity or expose private evaluator inputs.
